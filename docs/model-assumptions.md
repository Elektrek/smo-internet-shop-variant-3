# Правила моделирования и триггерные события

## Триггеры диспетчеров

**Диспетчер постановки** вызывается только событием генерации заявки (`ARRIVAL`). Он размещает запрос в буфере и не проверяет состояние приборов.

**Диспетчер выбора** вызывается по двум событиям:

1. `REQUEST_ENQUEUED` — заявка успешно появилась в буфере;
2. `SERVICE_COMPLETED` — освободился прибор.

После триггера диспетчер выбирает заявки только пока одновременно выполняются условия: в буфере есть ожидающая заявка и пул содержит свободный прибор. Если приборов нет, диспетчер завершает текущий вызов; он не крутится в пустом цикле и ждёт следующего триггера.

## Обработка событий

Календарь упорядочен по модельному времени. При одинаковом времени используется стабильный порядковый номер регистрации события, чтобы результат повторялся при одинаковом seed.

Минимальный набор типов событий:

- `ARRIVAL(sourceId)` — генерация заявки источником;
- `SERVICE_COMPLETION(workerId, requestId)` — завершение обработки на приборе.

Когда заявка генерируется, источник планирует следующую генерацию по экспоненциальному интервалу. При запуске обслуживания worker выбирает длительность `U(t_min, t_max)`, а календарь получает событие завершения в `now + serviceDuration`.

## Подробный порядок постановки

1. `PlacementDispatcher` вызывает у буфера поиск свободной ячейки по кольцу начиная с `putPointer`.
2. Если место есть, буфер сохраняет заявку и сдвигает указатель постановки.
3. Если места нет, буфер возвращает признак переполнения. Диспетчер выбирает старейшую ожидающую заявку (минимальное время постановки в буфер; при равенстве — минимальный sequence ID), удаляет её, учитывает вытеснение как отказ и размещает новую заявку.
4. После завершения операции движок инициирует `REQUEST_ENQUEUED` и запускает диспетчер выбора.

## Подробный порядок выбора и постановки на прибор

1. Диспетчер выбора проверяет наличие первого свободного прибора по возрастанию номера (`Д2П1`).
2. Если свободного прибора нет, заявки остаются в буфере.
3. Если прибор найден, буфер выбирает первую занятую ячейку, начиная с `selectionPointer` (`Д2Б3`); указатель выборки сдвигается.
4. Заявка получает отметку `serviceStartedAt`; worker переходит в `BUSY`; календарь планирует `SERVICE_COMPLETION`.
5. По завершении worker помечается `FREE`, статистика обновляется, и освобождение прибора триггерит диспетчер выбора повторно.
6. Если есть дополнительные свободные приборы и заявки в буфере, диспетчер повторяет выдачу, пока хотя бы одно из условий не перестанет выполняться.

## Что показывает пошаговый режим ОД1

Одна строка календаря на событие должна позволять восстановить состояние модели после обработки:

- модельное время, тип и краткое описание события;
- планируемое время следующей генерации каждого источника;
- занятость ячеек буфера с индексами `0..B-1`;
- `putPointer` и `selectionPointer`;
- для каждого прибора: `FREE/BUSY`, ID заявки и расчётное время завершения;
- накопленные значения `N_generated`, `N_completed`, `N_evicted`, доля отказов;
- текущее/среднее ожидание, среднее время в системе и загрузка приборов.

Календарь должен включать генерацию заявки, постановку в буфер/на прибор, вытеснение заявки, выборку из буфера, начало обработки и завершение обработки. Графики для кодов `ОР1`/`ОД1` по текущему описанию варианта не являются обязательными: автоматический режим выдаёт сводную таблицу, пошаговый — таблицу по каждому событию.

## Экономическое сравнение конфигураций

Для каждой конфигурации `(M, B)` нужно выполнить несколько прогонов и записать параметры, входные условия и выходные метрики. Для предметной области поиска товаров стоимость «прибора» корректнее моделировать как стоимость дополнительного вычислительного ресурса/worker-часа, а потерю от отказа — как оценку доли поисковых сессий, не получивших ответ. Итоговая стоимость одной успешно обработанной заявки:

`C_request = (C_compute + C_platform + C_loss_from_evictions) / N_completed`.

Все денежные параметры должны сопровождаться обоснованием источника; до получения этих данных денежный итог не рассчитывается.
