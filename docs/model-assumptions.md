# Правила моделирования и триггерные события

## Триггеры диспетчеров

**Диспетчер постановки** вызывается только событием генерации заявки (`ARRIVAL`). Он размещает запрос в буфере и не проверяет состояние приборов.

**Диспетчер выбора** вызывается по двум событиям:

1. `REQUEST_ENQUEUED` — заявка успешно появилась в буфере;
2. `SERVICE_COMPLETED` — освободился прибор.

После триггера диспетчер выбирает заявки только пока одновременно выполняются условия: в буфере есть ожидающая заявка и пул содержит свободный прибор. Если приборов нет, диспетчер завершает текущий вызов; он не крутится в пустом цикле и ждёт следующего триггера.

## Обработка событий

Календарь событий упорядочен по модельному времени. При одинаковом времени используется стабильный порядковый номер регистрации события, чтобы результат повторялся при одинаковом seed.

Минимальный набор типов событий:

- `ARRIVAL(sourceId)` — генерация заявки источником;
- `SERVICE_COMPLETION(workerId, requestId)` — завершение обработки на приборе.

Когда заявка генерируется, источник планирует следующую генерацию по экспоненциальному интервалу. При запуске обслуживания Worker выбирает длительность `U(t_min, t_max)`, а календарь получает событие завершения в `now + serviceDuration`.

## Подробный порядок постановки

1. `PlacementDispatcher` вызывает у буфера поиск свободной ячейки по кольцу, начиная с `putPointer`.
2. Если место есть, буфер сохраняет заявку и сдвигает указатель постановки.
3. Если места нет, буфер возвращает признак переполнения. Диспетчер выбирает старейшую ожидающую заявку (минимальное время генерации; при равенстве — минимальный sequence ID), удаляет её, учитывает вытеснение как отказ и размещает новую заявку.
4. После завершения операции движок инициирует `REQUEST_ENQUEUED` и запускает диспетчер выбора.

## Подробный порядок выбора и постановки на прибор

1. Диспетчер выбора проверяет наличие первого свободного прибора по возрастанию номера (`Д2П1`).
2. Если свободного прибора нет, заявки остаются в буфере.
3. Если прибор найден, буфер выбирает первую занятую ячейку, начиная с `selectionPointer` (`Д2Б3`); указатель выборки сдвигается.
4. Заявка получает отметку `serviceStartedAt`; Worker переходит в `BUSY`; календарь планирует `SERVICE_COMPLETION`.
5. По завершении Worker помечается `FREE`, статистика обновляется, и освобождение прибора вызывает диспетчер выбора повторно.
6. Если есть дополнительные свободные приборы и заявки в буфере, диспетчер повторяет выдачу, пока хотя бы одно из условий не перестанет выполняться.

## Что показывает пошаговый режим ОД3

В пошаговом режиме после каждого обработанного события отображаются **временные диаграммы и текущее состояние системы**. Диаграммы позволяют проследить изменение состояния элементов СМО во времени, а текущее состояние показывает их значения на момент завершения очередного шага моделирования.

Временные диаграммы должны отражать:

- поступление заявок от каждого источника;
- изменение занятости ячеек буфера;
- периоды занятости и простоя каждого прибора;
- моменты основных событий: поступление заявки, вытеснение, начало и завершение обслуживания.

Для текстового представления диаграмм могут использоваться следующие обозначения:

- `A` — поступление новой заявки;
- `C` — завершение обслуживания;
- `#` — занятая ячейка буфера;
- `█` — прибор занят обслуживанием;
- `·` — свободное состояние ячейки или прибора.

Под временными диаграммами на каждом шаге отображается текущее состояние системы:

- модельное время и последнее обработанное событие;
- состояние и планируемое время следующей генерации каждого источника;
- занятость ячеек буфера с индексами `0..B-1`;
- положения `putPointer` и `selectionPointer`;
- для каждого прибора: `FREE/BUSY`, ID обслуживаемой заявки и расчётное время завершения;
- накопленные значения `N_generated`, `N_completed`, `N_evicted` и доля отказов;
- текущее и среднее время ожидания, среднее время пребывания в системе и загрузка приборов.

Временные диаграммы обновляются после каждого обработанного события. История событий сохраняется в пределах отображаемого временного окна, чтобы можно было проследить изменение состояния системы.

Календарь событий используется внутри модели для определения ближайшего события и продвижения модельного времени. Отдельная таблица календаря событий в пользовательском пошаговом отображении не требуется.

## Автоматический режим ОР1

В автоматическом режиме моделирование выполняется без пошагового отображения. После завершения прогона формируются две итоговые таблицы с результатами моделирования и показателями эффективности системы.

К основным показателям относятся:

- количество сгенерированных заявок;
- количество успешно обработанных заявок;
- количество вытесненных заявок;
- доля отказов;
- среднее время ожидания;
- среднее время пребывания заявки в системе;
- загрузка каждого вычислительного прибора.

Графики параметров в автоматическом режиме для текущего варианта не требуются.

## Экономическое сравнение конфигураций

Для каждой конфигурации `(M, B)` нужно выполнить несколько прогонов и записать параметры, входные условия и выходные метрики. Для предметной области поиска товаров стоимость «прибора» корректнее моделировать как стоимость дополнительного вычислительного ресурса/Worker-часа, а потерю от отказа — как оценку доли поисковых сессий, не получивших ответ. Итоговая стоимость одной успешно обработанной заявки:

`C_request = (C_compute + C_platform + C_loss_from_evictions) / N_completed`.

Все денежные параметры должны сопровождаться обоснованием источника; до получения этих данных денежный итог не рассчитывается.
